# 课程学习知识库平台：RAG 检索层升级路线图

> 目标：将当前“关键词命中 + 大模型回答”的原型，升级为可解释、可评测、可扩展的混合 RAG 系统。
>
> 执行原则：一次只升级一个能力；每一阶段有明确验收标准；未通过验收不进入下一阶段。

---

## 0. 当前基线与最终目标

### 当前实现

- PDF 已能提取文字、页码与文字坐标。
- 文件、分块、笔记、对话与术语信息保存于 SQLite。
- 当前检索依赖关键词出现次数排序。
- 总控 Agent 可以跨全部科目检索；科目 Agent 仅检索单科目。
- 回答可附带科目、页码与原文片段。

### 当前主要限制

- 用户说法与课件原文不一致时，关键词检索常常召回失败。
- 相同关键词可能出现在多个章节，缺少语义相关性判断。
- 分块目前偏固定长度，章节语义容易被截断。
- 不能用指标判断“检索效果是否真的变好”。

### 升级后的检索链路

```text
用户问题
  → 查询规范化 / 路由
  → 关键词召回（BM25） + 语义召回（向量）
  → 融合排序（RRF）
  → 重排序（Reranker）
  → Top 3–5 证据片段
  → DeepSeek 受限生成答案 + 引用
```

---

## 1. 总体实施顺序

1. 建立检索评测基线
2. 优化 Markdown 结构化分块
3. 接入本地向量库与 Embedding
4. 实现混合检索与融合排序
5. 增加重排序
6. 增加查询改写与多 Agent 路由
7. 提升笔记检索与完成整体验收

建议不要跳过第 1 步。没有基线，就无法在答辩时证明检索层是否真正提升。

## 阶段 M0：建立可比较的检索评测基线

### 目的

用一组固定问题记录当前关键词检索的表现。后续每次升级都复测同一组问题。

### 要做什么

1. 在 `docs/evaluation_questions.json` 创建 20–30 个问题。
2. 每题人工标记：正确科目、正确文件、正确页码、关键答案片段。
3. 保存当前系统的 Top 5 检索结果。
4. 计算三项基础指标：
   - `Recall@5`：正确片段是否出现在前 5 个结果中；
   - `MRR`：正确结果第一次出现的位置；
   - `Citation Accuracy`：最终回答中的页码引用是否正确。

### 问题覆盖建议

- 明确术语：如“采样定理是什么？”
- 同义改写：如“怎么避免混叠？”
- 不记得科目：如“卷积神经网络是哪门课讲的？”
- 章节定位：如“第三章的损失函数如何定义？”
- 个人笔记：如“我之前对反向传播记了什么？”
- 无答案问题：如“文档中没有的概念是什么？”

### 验收标准

- 至少 20 道带标准答案的问题；
- 每题都标记正确文件与页码；
- 能输出当前关键词检索的 `Recall@5` 与 `MRR`。

### 完成后产物

- `docs/evaluation_questions.json`
- `docs/evaluation_baseline.md`

## 阶段 M1：结构化 Markdown 分块

### 目的

让每个检索片段具备完整上下文，避免在标题、段落或页码边界中间被截断。

### 设计原则

- 先按页码锚点分段；
- 再按标题层级（H1 / H2 / H3）聚合；
- 最后对过长段落做长度切分；
- 保留少量重叠窗口，避免上下文断裂；
- 每个 chunk 必须携带可溯源元数据。

### Chunk 元数据规范

```json
{
  "chunk_id": "file_uuid_p5_c03",
  "file_id": "file_uuid",
  "subject": "机器学习",
  "page": 5,
  "section_path": "第三章 / 神经网络 / 反向传播",
  "content": "...",
  "source_type": "courseware",
  "bbox_json": "[...]"
}
```

笔记写入时统一使用：

```json
{
  "source_type": "personal_note",
  "note_weight": 1.25
}
```

### 推荐参数

- 目标 chunk 长度：350–600 中文字符；
- 重叠长度：80–120 字符；
- 单页内容很短时，不强制拆分；
- 标题需与其正文进入同一个 chunk。

### 需要修改的模块

- 将 `main.py` 中的 `split_text()` 拆到 `services/chunk_service.py`；
- 新增 Markdown 解析、标题路径追踪与页码锚点解析；
- 扩展 SQLite `chunks` 表，增加 `section_path` 与 `source_type` 字段。

### 验收标准

- 随机检查 10 个 chunk：标题、正文与页码保持一致；
- 任何引用都能打开原 PDF 对应页；
- M0 评测集的 `Recall@5` 不低于当前基线。

## 阶段 M2：接入向量检索

### 目的

处理“问法不同、含义相同”的情况。

### 推荐架构

```text
SQLite：文件、chunk 元数据、对话、笔记
Chroma：embedding、chunk_id、subject、page、source_type
本地 Embedding 模型：中文语义向量模型
```

### 模型选择原则

- 毕设本地开发优先使用可本地运行的中文 Embedding 模型；
- 模型需支持中文、英文与中英混合术语；
- 不与 DeepSeek 聊天模型混用：聊天模型负责生成，Embedding 模型负责相似度检索；
- 模型名称和版本固定写入配置，保证复现实验。

### 实施任务

1. 增加 `vector_db/` 持久化目录。
2. 新建 `services/embedding_service.py`：加载模型与批量向量化。
3. 新建 `services/vector_store.py`：按 `subject` 建立 collection。
4. PDF 上传完成后，对新增 chunk 建向量索引。
5. 为已有课件提供“重建向量索引”按钮或后台任务。
6. 用 `chunk_id` 连接 Chroma 与 SQLite，避免向量库重复保存大段元数据。

### 单科与跨科检索规则

- 科目 Agent：只搜索 `collection = subject`；
- 总控 Agent：并行搜索所有 subject collection，每科先取 Top 3；
- 合并后去重，再进入统一排序。

### 验收标准

- 同义问法能命中正确片段，例如“防止混叠的方法”能召回“采样定理”；
- 服务重启后向量索引仍然存在；
- 每个结果都保留 `chunk_id / subject / page`。

## 阶段 M3：混合检索（BM25 + 向量）

### 目的

同时保留专业术语精确匹配和自然语言语义理解的优点。

### 为什么需要混合检索

- BM25 擅长：公式名、缩写、英文术语、人名、课程专有名词；
- 向量检索擅长：同义问法、口语化问题、概念解释；
- 课程场景中两者都不可替代。

### 实施方式

1. 在 SQLite 或内存索引中维护每个科目的 BM25 索引；
2. 向量检索取 Top 20，BM25 取 Top 20；
3. 使用 RRF（Reciprocal Rank Fusion）融合两个排序结果；
4. 笔记结果加入权重提升，例如 RRF 分数乘以 `1.15–1.25`；
5. 将融合后 Top 20 交给下一阶段的重排序。

### RRF 说明

```text
score(chunk) = Σ 1 / (k + rank_i)
```

其中 `rank_i` 是该 chunk 在向量或 BM25 检索中的名次，`k` 可从 60 开始。

### 验收标准

- 术语类问题不能比纯 BM25 更差；
- 同义类问题不能比纯向量更差；
- M0 评测集的 `Recall@5` 高于 M0 基线。

---

## 阶段 M4：重排序（Reranking）

### 目的

从“相关”候选里找到“最能直接回答问题”的证据片段。

### 实施任务

1. 混合检索先召回 Top 20；
2. 调用重排序模型，对 `(用户问题, chunk)` 成对评分；
3. 取分数最高的 Top 3–5 作为最终上下文；
4. 对相邻页、相同章节的片段做去重或合并；
5. 将重排序分数写入调试日志，便于答辩展示。

### 方案选择

- 优先：本地 Cross-Encoder 重排序模型，延迟更稳定；
- 原型备选：让 DeepSeek 对 Top 10 片段排序；
- 不建议直接把全部课件传给大模型排序。

### 验收标准

- 正确证据在 `Top 3` 出现的比例提升；
- 引用片段更短、更直接；
- 单次问答延迟仍在可接受范围内。

## 阶段 M5：查询改写与多 Agent 路由

### 目的

让系统更好理解模糊问题，并正确选择单科或跨科检索。

### 路由流程

```text
用户问题
  → 判断是否已选定科目
  → 判断是否出现跨科线索（“哪门课”“之前学过”“在哪份资料”）
  → 单科 Agent 或总控 Agent
  → 查询改写
  → 混合检索 + 重排序
```

### 查询改写要求

- 只改写检索查询，不替用户编造事实；
- 输出 1 个主查询 + 最多 3 个扩展关键词；
- 保留专业术语、公式名、英文缩写；
- 查询改写过程不写入用户对话历史。

### 总控 Agent 的边界

- 可检索全部科目知识库；
- 不读取各科目 Agent 的聊天记录；
- 合并的是文档片段，不是会话上下文。

### 验收标准

- “不知道属于哪门课”的问题可跨库定位；
- 指定科目时不会错误召回其他科目；
- 总控 Agent 的回答仍提供科目与页码引用。

---

## 阶段 M6：笔记增强与最终评测

### 目的

让用户的标注和笔记成为高价值个人知识，而不只是 PDF 附件。

### 实施任务

1. 笔记写入后同时更新：PDF 高亮、Markdown、SQLite、向量库、BM25 索引；
2. 笔记 chunk 增加 `source_type=personal_note`；
3. 提问中出现“我记得”“我的笔记”“之前标注”时，提高个人笔记权重；
4. 回答引用中清晰标记“课件原文”或“我的笔记”；
5. 跑完整 M0 评测集，形成最终实验结果。

### 最终答辩可展示指标

- 关键词基线 vs 向量检索 vs 混合检索的 `Recall@5`；
- 是否使用重排序前后的 `MRR`；
- 单科问题与跨库问题的成功率；
- 笔记召回命中率；
- 回答引用正确率。

### 验收标准

- 新笔记保存后无需重新上传 PDF 即可被问答检索；
- 引用可跳转到原 PDF 页；
- 输出一份可用于论文的评测结果报告。

## 4. 我们接下来的节奏

### 第一次升级：只做 M0

先建立 20 道评测问题与当前检索结果，不改检索代码。这一步约 30–45 分钟，完成后我们才有改进参照。

### 第二次升级：完成 M1 + M2

完成结构化分块和向量检索，先让单科检索变准，再扩展总控 Agent。

### 第三次升级：完成 M3 + M4

接入混合检索和重排序，重点提升 Top 3 证据质量。

### 第四次升级：完成 M5 + M6

加入查询改写、跨库路由和笔记权重，最后形成论文实验结果。
